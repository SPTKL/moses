# PLUTO source inventory and reproduction boundary

Inspected 2026-10-17 at data-engineering commit `5b849eebf4afbe282f30944cfbedd918bc51ad81`. This is a static, evidence-backed inventory; endpoint URLs below are configured locators, not a claim of successful live downloads. See the separate case-study run report for tested coverage.

The major PLUTO recipe has **38 source datasets**, plus **11 version-controlled CSV seeds**. PLUTO is a suitable Moses integration case because it combines public downloads, APIs, managed object storage, credentialed inputs, spatial transformations, and manual corrections. Loading published PLUTO is a baseline; it does not reproduce the PLUTO build.

The machine-readable [inventory](../examples/pluto/inventory.json) preserves every recipe entry, raw source configuration, parse options, processing steps, declared columns, CRS declarations, access class, and major/minor version policy. It deliberately leaves live verification false.

Execution tracking: [#17 — PLUTO case study](https://github.com/SPTKL/moses/issues/17), [#18 — major/minor recipe resolution and manifests](https://github.com/SPTKL/moses/issues/18), [#19 — reference build parity](https://github.com/SPTKL/moses/issues/19), and [#20 — source contracts](https://github.com/SPTKL/moses/issues/20). Source-contract findings need fixture-based acceptance checks.

## Raw source versus build input

The upstream templates describe extraction and transformation of raw sources. The PLUTO recipe normally consumes archived **normalized EDM recipe datasets**, with default connector `edm.recipes.datasets`. The planner prefers `pg_dump`, then Parquet, then CSV; only ZIP codes and FEMA 2007 explicitly request Parquet. Moses should record both raw-capture lineage and normalized-artifact lineage. A public API sample is not interchangeable with the historical artifact used by a specific PLUTO release. Sources: [python/lifecycle/dcpy/lifecycle/builds/models.py](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/python/lifecycle/dcpy/lifecycle/builds/models.py), [python/lifecycle/dcpy/lifecycle/builds/plan.py](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/python/lifecycle/dcpy/lifecycle/builds/plan.py).

## Version and reproducibility rules

- **Major:** `bump_latest_release`, `version_type: major`, and `missing_versions_strategy: find_latest`. Every unpinned source resolves at planning time; `dcp_pluto` imports as `previous_pluto` using `VERSION_PREV`. [Major recipe](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/recipe.yml).
- **Minor:** inherits all major inputs. `copy_latest_release` keeps source versions from the latest published PLUTO manifest, except eight zoning/E-designation sources explicitly set to `latest`, plus `dcp_developments` as a documented temporary planning workaround. Previous PLUTO still uses `VERSION_PREV`. The eight sources are E-designations, commercial overlays, limited heights, zoning districts, special-purpose districts/subdistricts, zoning map amendments, and zoning map index. [Minor recipe](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/recipe-minor.yml).
- **Locked execution:** planning resolves `latest` to concrete connector versions and writes `recipe.lock.yml`, `build_metadata.json`, and `source_data_versions.csv`. Moses must lock each upstream version, acquired bytes hash, accepted Moses version, schema/CRS, transform specification, and code/runtime version. It must fail clearly when a required historical capture is unavailable. [Planner](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/python/lifecycle/dcpy/lifecycle/builds/plan.py).
- **Private/managed inputs:** approved captured files can exercise the Moses parser locally without embedding credentials. Record why a dataset is blocked, its owner, and the evidence needed to unblock it. Do not substitute a public derivative and label the run equivalent.

The recipe stage list omits the separate export shell command; use the workflow as well as the recipe when defining reproduction. [Build workflow](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/.github/workflows/pluto_build.yml); [PostgreSQL dbt profile](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/profiles.yml).

1. Plan and lock the recipe; load archived inputs into the build schema, using cached recipe views.
2. Load all local seeds and materialize dbt staging models. Staging adapts geometry names and creates spatial indexes; this is not merely a file copy.
3. Execute SQL for PTS/RPAD, condo prime-BBL allocation, base PLUTO, Geosupport-derived geography, CAMA, other attributes, DTM geometries, zoning, spatial enrichment, flood flags, political boundaries and shoreline clipping.
4. Run dbt enrichment models and apply results back to PLUTO: FAR, irregular lots, condo numbers, historic/landmark flags, numeric fields, lat/long, MIH and transit zones.
5. Apply manual corrections, remove unit lots, and prepare CSV/MapPLUTO export tables.
6. Compare with previous-release QA artifacts: BBL differences, expected values, aggregate, mismatch, null and outlier reports; retain mapped/unmapped and condo/non-condo slices.
7. Export PLUTO CSV, clipped/unclipped MapPLUTO shapefiles and geodatabases, correction reports, source versions and build metadata; upload via publishing connector.
8. Run source tests and dbt QA reports, then release-type-specific `de_check` tests. Note that this workflow runs custom QA after upload: Moses acceptance/publishing design should make the validation gate explicit.

PLUTO lot geometry is constructed in EPSG:4326; calculations and output geometry use EPSG:2263 where specified. Moses must distinguish CRS assignment from reprojection and retain source/target CRS and axis conventions. [Lot geometry](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/pluto_build/sql/plutogeoms.sql); [Projected export geometry](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/pluto_build/sql/shorelineclip.sql); [State-plane coordinates](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/pluto_build/sql/create_rpad_geo.sql).

The dbt project depends on `dbt_utils` 1.3.2, `audit_helper` 0.13.0 and `dbt_expectations` 0.10.9; the profile is PostgreSQL. Porting shell/psql variables, mutable SQL, PostGIS operators, spatial indexes, geometries, and package behavior to DuckDB requires measured parity work. The first orchestration milestone should wrap an isolated reference PostGIS build rather than assume all SQL already runs in Moses. [dbt packages](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/products/pluto/packages.yml).

## Concrete blockers and usability findings

1. **CAMA availability and silent failure:** the template explicitly says it is not production-ready, the file is not always present, and the raw output was not retained for validation. The weekly input workflow sets `error_behavior: ignore` for CAMA and explicitly notes that this ignores all errors. A successful-looking run must distinguish missing optional capture, stale accepted version, parse failure and ready input. [CAMA warning](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/ingest_templates/pluto_input_cama_dof.yml); [Weekly input workflow](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/.github/workflows/pluto_inputs.yml).
2. **Possible geocode axis reversal:** the geocode template declares `x: latitude`, `y: longitude`; the processing function defaults to EPSG:4326 and passes x/y through to geometry construction. This conflicts with the usual longitude/latitude order and the PLUTO download template. Reproduce on an approved fixture and assert expected NYC bounds before adopting this step; this inventory does not claim to have reproduced its effect on production output. [Geocode template](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/ingest_templates/pluto_input_geocodes.yml); [Geometry processing](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/python/lifecycle/dcpy/lifecycle/ingest/transform.py); [Point construction](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/python/geospatial/dcpy/geospatial/transform.py).
3. **Misleading source metadata:** transit zones link to a Historic Districts URL (`skyk-mpzq`), while the actual extraction uses `6ztr-wgff`. The source detail page should show actual connector ID and capture evidence, not trust the human-facing URL as execution provenance. [Transit zones template](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/ingest_templates/dcp_transit_zones.yml).
4. **Derived sources are not raw source parity:** geocodes require Geosupport; number-of-buildings starts from building-footprints BINs, geocodes them and groups by BBL. Ingesting a footprint sample alone does not reproduce `pluto_input_numbldgs`. The template itself recommends making this a build transformation. [Building-count derivation](https://github.com/NYCPlanning/data-engineering/blob/5b849eebf4afbe282f30944cfbedd918bc51ad81/ingest_templates/pluto_input_numbldgs.yml).
5. **Source readiness is a product feature:** the user needs one checklist with verified/partial/blocked, exact version, format, CRS, key validation, observed rows, capture time, errors and the next action. A few successful public files must not imply all 38 recipe inputs are ready.
6. **Missing release fixtures:** complete input lock, reference outputs, prior QA artifacts, Geosupport version and approved managed-source captures are required for a meaningful reproduction verdict. Source URLs and latest API data alone cannot establish historical parity.

## Phased reproduction milestones

| Milestone | Parallel owner | Acceptance evidence |
| --- | --- | --- |
| M0: Representative public ingestion | Connector/integration agent | One actual PLUTO recipe source per available transport: versioned download, Socrata and ArcGIS. Record request, bytes hash, scope (sample/full), schema, CRS, complete-key checks and Moses accepted version. Reingest identical bytes and check immutable-version behavior. |
| M1: Complete source readiness | Source/access agent | All 38 inputs and 11 seeds accounted for; blocked inputs explicit; approved PTS/CAMA and managed GIS/storage captures available; derived-source contracts specified. No secrets in manifests. |
| M2: Locked build inputs | Recipe/lineage agent | Major and minor resolution produces reproducible concrete input versions; no floating latest during execution; raw and normalized hashes linked; previous-release inputs and QA captured. |
| M3: Reference build orchestration | Build agent | Run pinned upstream SQL/dbt in isolated PostGIS against the locked capture; collect correction logs, QA outputs and final exports. No production publishing. |
| M4: Incremental transformation parity | Transform agent | Port bounded groups of SQL/dbt transforms only after comparing BBL presence, types, nulls, field-level values and spatial results against the reference; document accepted geometry/float tolerance. |
| M5: Reproducible PLUTO release candidate | QA/release agent | Complete locked build reruns with matching defined checks; failure leaves last accepted version unchanged; outputs expose lineage and QA summary; senior-PM walkthrough identifies actionable roadmap issues. |

Run PM review at every milestone: can an analyst identify what was loaded, distinguish samples from complete sources, understand and repair an error, rerun the same inputs, compare changes, and explain why a result is accepted? File issues with observed evidence, user impact, acceptance criteria and dependencies.
